# 证据口径与状态契约

这份文件是整仓库的地基。它规定两件事：**一句话凭什么算成立**，**一个功能凭什么算做完了**。

不先立这两条，后面的内容无论多详细都只是观点集合。

## 一、状态四态（做什么算完成）

这四个状态经常被合成一个「已完成」，然后所有后续判断都建在流沙上。

| 状态 | 含义 | 判定依据 |
|---|---|---|
| 已部署 | 文件在、依赖能导入 | 路径存在、`import` 退出码 0 |
| 能启动 | 入口不崩 | `--help` 或空跑返回 0 |
| 实跑通过 | 真实输入走完整条 | 退出码 0 **且**产物结构校验通过 **且**覆盖区间符合预期 |
| 质量验收 | 结果可用 | 抽样人工核对，错误率在约定范围内 |

**越级的典型错误**：

- 模型文件存在 → 宣布「转写可用」（停在已部署，跳到质量）
- CLI 返回 0 → 宣布「识别准确」（停在能启动，跳到质量）
- 输出 JSON 落盘 → 宣布「流程闭环」（失败前也会落盘）
- 沙箱里读到 `MPS available = False` → 宣布「机器不支持」（是环境限制，不是硬件结论）

**本仓库自己的声明**：本仓库是方法论文档，不包含可执行代码。因此它对自身只声明到「已交付文档」这一层，**不声明任何一条采集链路当前可用**——平台接口会变，可用性必须每次实测。

## 二、证据四级（一句话凭什么算成立）

| 级别 | 含义 | 可以怎么说 |
|---|---|---|
| A · 本机实测 | 在自己机器上跑通并看到结果 | 「实测返回 X」+ 日期 + 环境 |
| B · 官方声明 | 平台文档 / 维护者仓库写明 | 「官方文档称 X」+ 链接 |
| C · 分析者建议 | 基于前两者的推断 | 「建议按 X 处理」 |
| D · 仍待验证 | 没测、没有可靠来源 | 「未验证，不作结论」 |

**引用规则**：

1. 每条结论必须能标到 A / B / C / 某一级，标不出级别的删掉
2. **B 不能当 A 用**：官方说支持 ≠ 本机能跑通；厂商基准 ≠ 本机基准
3. **C 不能写成结论**：建议要带条件和代价，不能伪装成事实
4. D 级必须显式写「未验证」，不许用「可能 / 通常 / 一般来说」蒙过去

## 四、两类最容易发生的越级

**把「算得出来」当「有意义」。** 一个比率能算出来，不代表它高于偶然水平。任何命中率、对齐率、重合率类指标，先问一句：随机情况下的基线是多少？算不出基线，就把它降级为描述性数字，不给结论。

**把「跑完了」当「做对了」。** 进程退出 0 只说明没崩。完成的标准是：退出码 + 结构校验 + 覆盖区间三者同时成立。三者缺一，产物只能是中间产物。

这两条越级，代价都不是返工一次，而是**在错误的结论上继续叠加工作**。
