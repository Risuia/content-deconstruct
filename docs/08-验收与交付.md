# 验收与交付

前面的分册讲怎么拆，这一篇讲**怎么证明拆完了**。没有这一环，前面的内容只是一套说法。

## 一、一次拆解的验收对象

不要只验收最后的报告。一次拆解有四个产物，每个都要单独过：

| 产物 | 验收什么 | 不通过的表现 |
|---|---|---|
| 证据包 | 采集覆盖区间、条数口径、时间戳合法性 | 声明条数 ≠ 实际条数；时间戳逆序 |
| 可读稿 | 疑难词标记、修改可追溯 | 把整理稿称作「原始逐字原文」 |
| 归因报告 | 每条结论可回溯到证据 | 引文定位不到原文 |
| 索引记录 | 作品 ID、创作者、日期、状态 | 系列里断档，找不到上一份 |

**四条同时成立才算交付。** 报告写得再好，证据包口径不对，整份作废。

## 二、完成状态怎么判

沿用 [`00-证据口径与状态契约.md`](00-证据口径与状态契约.md) 的四态，落到每个阶段：

| 阶段 | 完成判定 |
|---|---|
| 采集 | 退出码 0 + 目标字段非 null + 业务 `code` 为 0 + 条数 > 0 |
| 转写 | 退出码 0 + 段数与时长匹配 + 无整段重复 |
| 对齐 | 至少三个带秒数的判断，且都能回查 |
| 报告 | 七个章节齐全 + 无未渲染占位符 + 引文可回溯 |

**「文件存在」不是完成。** 失败前也会落盘，这条在转写和视听对齐上都实际发生过。

## 三、最小验收样本

不需要全库人工核对。选 6 类、每类挑 1 条、每条只看 60 至 120 秒，就足以暴露系统性问题：

| 样本类型 | 想验证什么 |
|---|---|
| 标准单人口播（有分章） | 基线是否成立 |
| 口误多、语速快 | 转写的错误率是否可接受 |
| 无分章、弹幕稀疏 | 结构能否靠弹幕时序反推 |
| 图文笔记（小红书） | 无时间信号时是否老实降级 |
| 纯图 / PPT 式视频 | OCR 路线是否该启用 |
| 录音循环或前段无关 | 有效区间识别是否可靠 |

每类只要求**人工参考 60 至 120 秒**，不要求全片听校。这是成本与结论强度之间的平衡点。

## 四、每次要记录的字段

不记录就等于没测，下次还会重复踩。

- 实际后端与模型版本、参数、语言
- 冷启动与热运行耗时、实时系数（处理耗时 / 素材时长）
- 弹幕与评论的**采集量 / 平台总量**两个口径
- 引文可回溯率（抽查 10 条，能定位到具体秒数的比例）
- 疑难词错误类型：人名、金额、否定词、说话人归属
- 校对分钟数
- 失败与重跑次数

**不测量就不填估计值。** 估计值当实测用，是这份工作里最贵的错误。

## 五、交付五件套

一次完整的拆解交付这五样，不要等对方追问才补：

1. **证据包**（JSON）—— 带时间戳的原始数据
2. **可读稿**（Markdown）—— 清理标点版式，修改留痕
3. **归因报告** —— 按 [`04-输出格式.md`](04-输出格式.md) 的骨架
4. **索引记录** —— 作品 ID、创作者、日期、置信度、状态
5. **状态表** —— 哪一步实测通过、哪一步只是跑起来、哪一步未做

第 5 项最容易被省，也最容易被误读。没有它，前四项会被当成「整条链路已验证」。

## 六、交付时怎么描述自己的工作

一句话模板，缺任何一段都不算说清楚：

> 本次在【环境】上实测了【哪几步】，通过标准是【退出码 / 结构 / 覆盖区间】；
> 未做【哪几步】，因此不能得出【哪些结论】；
> 已知限制【哪些】，重跑方式是【一条可复现命令】。

## 七、失败时的处理

- 失败只重跑对应片段，不重跑整条链路
- 缓存键至少绑定：源文件哈希、有效区间、后端与模型版本、语言、参数
- 底稿更新后，引用旧段号的分析自动标为待更新
- 拿不到的证据就写「未采集」，不要用相邻证据替代

**不要为了凑齐报告而补数据。** 报告缺一节是瑕疵，补一节假数据是失效。
