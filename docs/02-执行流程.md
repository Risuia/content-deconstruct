# 执行流程

五步，顺序不能跳。每一步都写清「做完的标志」，避免做到一半无法判断是否该往下走。

## 第 0 步 · 固定请求头

B站接口不带完整浏览器头会返回 `{"code":-352}` 而不是数据。这是第一步，不是排错时才想起的补救。

```bash
UA="Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36 (KHTML, like Gecko) Chrome/120.0.0.0 Safari/537.36"
curl -s -A "$UA" -H "Referer: https://www.bilibili.com/" "https://api.bilibili.com/..."
```

**完成标志**：同样的 URL 带头发请求返回 `code:0`，裸请求返回 -352。

## 第 1 步 · 定位候选

按**互动效率**排序，不按绝对播放量。绝对量会被大号碾平：100 万粉的号拿 10 万播放是失败，1 万粉的号拿 10 万播放是爆款。

| 平台 | 排序信号 |
|---|---|
| B站 | 投币率高 = 硬核认可；收藏率高 = 干货；评论率高 = 争议 |
| 抖音 | `hot_value` 绝对值 + `video_count`（关联视频数 = 热点宽度） |

B站三个信源各有用途：`popular` 看当下在涨的，`ranking/v2` 看官方按质量排的 100 条（更适合找强内容），`search/square` 给 30 条热搜词（与抖音交叉验证用）。

**完成标志**：手上有一份候选清单，每条带效率指标，而不是一份播放量排行榜。

## 第 2 步 · 取证据（B站四路并行）

**oid 类型必须分清：弹幕用 `cid`，评论用 `aid`。填错静默返回空，不报错。**

| 路 | 接口 | 拿到什么 |
|---|---|---|
| ① | `x/web-interface/view/detail?bvid=` | 元数据、标签、合集、荣誉、封面、首帧 |
| ② | `x/player/wbi/v2?bvid=&cid=` | 官方分章 `view_points`，含秒级 from/to 与每章封面图 |
| ③ | `x/v1/dm/list.so?oid={cid}` | 全量弹幕，带秒级时间戳 |
| ④ | `x/v2/reply?type=1&oid={aid}&sort=2&ps=20` | 评论，含点赞数与回复数 |

`ps` 上限 20，传 25 报 `-400 ps out of bounds`。

**完成标志**：弹幕条数 > 0 且时间戳分布覆盖全片。只有评论没有弹幕的话，后面只能做争议点，不能做结构。

## 第 3 步 · 看画面

三条免费路径：封面 `pic`、首帧 `first_frame`、分章封面 `view_points[].imgUrl`。

分章封面是官方精挑的关键帧，**等于一份免费分镜表**，比随机抽帧质量更高。先读这三样，不够再抽帧。

读图要回答的具体问题：构图（主体位置 / 留白）、花字（有无 / 大小 / 位置 / 颜色）、人物状态、色彩策略（主色调与情绪是否匹配）、信息密度、封面与首帧的职能差异。

**完成标志**：能说出封面在承诺什么、首帧在兑现什么，两者是否一致。

## 第 3.5 步 · 深挖（可选）

需要看画面动态或补口播原文时才做。零配置零 Key，只多一个 pip 包。

```bash
python -m pip install yt-dlp imageio-ffmpeg
python -m yt_dlp -f "30080+30280" --no-playlist -o "dl.%(ext)s" "https://www.bilibili.com/video/{BV}"
FF=$(python -c "import imageio_ffmpeg;print(imageio_ffmpeg.get_ffmpeg_exe())")
"$FF" -i dl.mp4 -vf "fps=1/8,scale=480:-1" -q:v 3 frames/f_%03d.jpg -y
```

实测 97 秒视频 → 12 帧，足以读出画面主体、水印、底部字幕、构图与色调。

**纯图 / PPT 式视频不要固定间隔抽帧**，用场景切换检测 `select='gt(scene,0.3)'`，否则会抽出几十张重复帧。

## 第 3.6 步 · 字幕（需登录态）

免登录只有 `danmaku` 轨，拿不到 `ai-zh`。三个坑：

- `--no-simulate` 必需，否则只打印不落盘
- `--cookies-from-browser` 仅在目标浏览器未运行时可用；否则用 Playwright 的 `context.cookies()` 取 HttpOnly cookie
- 验证标准：`--list-subs` 输出出现 `ai-zh` 行才算拿到登录态

拿不到就别反复请求——`need_login_subtitle:true` 时反复试只会触发风控。改用「分章 + 弹幕 + 封面图 + 评论」组合替代。

## 第 3.7 步 · 抖音与小红书

走浏览器插件复用已登录会话，不碰签名逆向。

| 工具 | 覆盖 | 特点 |
|---|---|---|
| MediaClaw MCP | 小红书 / 抖音 / TikTok | 浏览器插件 + STDIO MCP，40+ 工具，自带带时间戳的逐字稿 |
| OpenBiliClaw | 抖音 | Chrome 插件，从首页 DOM 触发 search / hot / feed |
| xhs-mcp | 小红书 | Playwright + 扫码登录，`get_note` 需先从 search 取 `xsecToken` |
| douyin-mcp | 抖音 | 本地 V8 生成 a_bogus，只需 cookies.txt |

小红书铁律：`note_url` 必须原样保留，含 `xsec_token` 等 query 参数。**用 note_id 重新拼链接读不到内容。**

## 第 4 步 · 对齐时间轴

把弹幕、分章、评论压到同一条时间线上，回答四个问题：

1. 钩子在第几秒生效（前 3 秒弹幕是否出现，出现的是什么情绪）
2. 哪个瞬间弹幕爆发（密度峰值 = 高光或争议点）
3. 观众从哪一刻开始质疑（负面弹幕的起点）
4. 结尾引导是否奏效（末段弹幕是否回应了引导语）

**这一步是拆解与复述的分界线。** 跳过它，后面的输出再漂亮也只是摘要。

**完成标志**：能给出至少三个带具体秒数的判断，且每个都能在弹幕或分章数据里指回去。

## 第 5 步 · 归因输出

按 [`04-输出格式.md`](04-输出格式.md) 的骨架写。每条结论标注证据来源（哪个接口的哪个字段、哪个时间戳），并给出置信度与缺失说明。

**完成标志**：随便抽一条结论，都能在两分钟内定位到原始证据。
